## 2. 샘플과 로컬 보관

- 사용자가 경로를 지정하면 그 경로를 사용한다. 제안 기본 경로는 저장소 밖의 `/Users/andyoon/stt-t16-samples/`다. 실제 강의 **각 10–15분, 최소 3개**를 사용한다. 긴 원본에 시작·끝 시각을 지정해도 된다. 독립된 구간이면 같은 강의에서 골라도 된다. 한국어 설명, 영어 전공 용어가 섞이는 설명, 평소 강의실의 음향 조건이 표본에 반영되면 좋다.
- 원본은 읽기 전용으로 사용한다. 파일의 디코딩 가능 여부와 구간 길이를 확인한다. 부족한 샘플이나 불분명한 시각은 구체적으로 요청하고, 모델·도구 준비와 합성 입력 검증은 계속한다. 사용자에게 30초 단위 분할이나 전체 정답 전사를 맡기지 않는다.
- 원음·PCM·실제 전사·정답 발췌·로그·개인 식별 경로는 로컬에만 둔다. 공용 benchmark report의 `input.audio.samples`에도 녹음이 들어 있다. 결과 저장소 예시는 Git에서 무시하는 `benchmark-results/t16/<실행 ID>/`다. 기존 실행 결과를 보존한다. 채팅에는 로컬 링크와 비식별 집계를 제공하고, Git에는 도구·합성 테스트·고정 모델 메타데이터·비식별 통계·결정 근거만 포함한다. 실제 샘플과 전사를 외부 서비스나 CI에 전송하지 않는다.

## 3. 비교 후보와 모델 준비

| 엔진 | 기준 후보 | 비교 후보 |
| --- | --- | --- |
| WhisperKit | T14 비양자화 large-v3 | 비양자화 large-v3-turbo의 호환 Core ML 패키지 |
| whisper.cpp | T15 비양자화 large-v3 | 비양자화 large-v3-turbo의 호환 GGML 패키지 |

T14/T15의 고정 엔진 revision과 기존 후보 manifest를 재사용한다. 개발용 모델 저장소 후보는 `/private/tmp/stt-t14-offline/store`, `/private/tmp/stt-t15-validation.Uth8xp/store`다. 임시 경로이므로 실행 시 존재와 무결성을 확인한다. 필요한 비교 후보와 토크나이저는 검증 가능한 공개 출처에서 명시적으로 준비하고 기존 T12/T13 설치·검증 경로를 이용한다. 설치 이후 강의 비교 전체를 오프라인에서 실행한다. 자동 업데이트·제품 카탈로그·기본값은 이 작업의 대상이 아니다.

`WhisperKitSTTEngine.swift`의 공용 어댑터는 현재 variant를 large-v3로 제한한다. `WhisperKitModelValidator.swift`, `WhisperCppModelValidator.swift`, 네이티브 가중치 snapshot 경로 및 CLI의 보고 문구에도 기존 모델 전용 값이 있다. 두 turbo 후보의 실제 revision·파일 크기·SHA-256·형식·아키텍처·토크나이저·정밀도·라이선스를 확인하고 후보별로 **명시적이고 좁게** 지원한다. 기존 large-v3 검증과 lease/취소/오프라인 계약을 보존한다. 이름만 바꾼 descriptor, 임의 모델을 통과시키는 validator, 엔진 외부 CLI의 출력은 비교 근거로 쓰지 않는다.

네 후보에 모든 샘플을 실행한다. 특정 조합이 실제로 지원되지 않으면 시도한 조합, 실패 증거와 빠진 비교를 기록하고 나머지를 수행한다. 대체 후보나 범위 변경이 필요하면 사용자에게 결정받는다. `medium`은 큰 모델들의 처리량이 부족한 경우, 양자화는 여전히 성능이 부족한 경우에 검토한다. 후보를 조용히 줄이거나 미측정값을 점수로 채우지 않는다.

## 4. 긴 강의를 같은 조건에서 처리

1. `tools/t14/BenchmarkMain.swift`의 기존 prepare 입력 한도는 mono 16 kHz, 최대 480,000프레임(30초)다. `STTBenchmarkRunner.measure`는 단일 요청마다 load/start/end/unload를 수행하고 비어 있는 전사를 실패로 간주한다. 기존 smoke 명령은 보존하고 최소한의 개발자용 배치 경로를 만든다. 후보·샘플별 측정 실행 동안 모델을 한 번 로드하고 한 세션에서 순서대로 마지막 구간까지 `STTEngine`을 통해 추론한다.
2. 각 지정 구간을 **한 번만** 16 kHz mono Float32로 변환한다. 원본 및 PCM 해시, 프레임 수, 변환·채널 혼합 설정과 공통 구간표를 로컬 manifest에 기록한다. 예를 들어 겹치지 않는 20초 구간과 마지막 짧은 구간을 사용한다. 네 후보의 입력 해시·시작/끝 프레임·순서를 대조하고 전체 프레임 합계로 누락과 중복을 확인한다. 타임스탬프는 샘플 시간축에 맞추고 긴 원본에서 발췌한 경우 원본 재생 위치도 표시한다.
3. 같은 Mac에서 후보를 순차 실행한다. 샘플별 언어 모드를 고정하고 한국어 중 영어 용어가 섞이는 강의에는 한국어 transcribe를 쓴다. hints, temperature, 부분 결과·타임스탬프, 워밍업과 측정 횟수·순서를 먼저 정해 동일하게 적용한다. 엔진 고유 compute·디코딩 설정은 기록한다. 정답 메모는 채점에만 쓴다.
4. 각 구간의 terminal, 텍스트, 시간, 실패·재시도·경고를 보존한다. 무음의 정상적인 빈 final과 추론 실패를 구분한다. 후보·샘플별 전체 처리율과 빠진 구간을 표시한다. 결과가 좋은 구간만 발췌해 완주로 보고하지 않는다.
5. 완주한 샘플의 RTF는 **총 추론 시간 ÷ 총 오디오 시간**이다. 로드·워밍업은 별도 기록한다. 구간 제출 후 첫 partial·final까지의 지연, 대기·적체, 동일한 방식의 baseline/peak physical footprint, 오류·안정성을 기록한다. partial 미관측은 그대로 표시한다. 순차 배치라면 실제 구간 도착 시각과 서비스 시간을 사용해 실시간 유입 시의 대기를 모의하고 계산식과 결과에 모의치라고 표시한다. 두 엔진의 partial 발생 단위와 메모리 측정 한계를 명시한다. 17.1의 RTF 0.83·지연 목표와 비교할 때 배치 제출 지연과 마이크 발화 기준 지연, 2시간 라이브 안정성을 구분한다.

## 5. 평가와 사용자 선택

| 명세 17.5 항목 | 비중 | 근거 |
| --- | ---: | --- |
| 한국어 본문 정확도 | 40% | 같은 발화의 의미와 표기 오류. 참조가 있는 구간에 한해 문자 오류율 등 사용 가능 |
| 영어 및 전공 용어 보존 | 25% | 원음에서 확인한 용어·약어별 보존/오류 사례와 분모 |
| 환각·반복·누락 | 20% | 원음과 전사를 대조한 사건의 종류·빈도·영향·위치 |
| 실시간 지연과 대기열 | 10% | 첫 partial·final 지연 분포, RTF, 대기열 측정 또는 모의 결과 |
| 메모리와 안정성 | 5% | peak footprint, 완주율, 중단·실패·재시도 |

- 미리 공통 채점 척도와 집계 방법을 정한다. 예를 들어 각 항목이 0–5점이면 총점은 `Σ(항목 점수 / 5 × 비중)`으로 100점 만점이다. 원값·분모·관찰 근거와 사람의 평가를 함께 둔다. 미평가 항목이 있으면 완성된 총점·순위를 만들지 않는다.
- 전체 정답 전사가 없어도 진행한다. 평가용 대표 구간을 후보 출력과 독립적으로 선정한다(예: 각 샘플 초·중·후반). 네 후보의 같은 구간을 나란히 보여주고 원음을 같은 위치에서 확인할 수 있게 한다. 오류가 두드러진 구간은 추가 예시로 구분한다. 사용자가 짧은 정답/용어 메모를 제공하면 해당 구간에만 적용한다. 참조가 부족하면 재생 위치가 있는 검토표와 간단한 채점란을 제공해 사용자가 판단할 수 있게 한다. 엔진 간 일치나 타 엔진 출력을 정답으로 취급하지 않는다.
- **로컬 검토 파일 하나**(예: `REVIEW.md`)에서 시작할 수 있게 한다. 후보별 요약·장단점, 샘플별 같은 구간의 전사 비교, 원음 재생 위치, 전체 전사·상세 측정 링크를 포함한다. 사용자에게 이 파일과 가능한 엔진·모델 조합을 제시하고 **어느 조합을 기본값으로 선택하는지 명시적으로 묻는다**. 최고점이나 무응답만으로 결정하지 않는다.
- 같은 세션에서 사용자 답변을 받은 뒤 날짜, 선택한 엔진·모델·revision·checksum·compute 설정, 사용자가 밝힌 이유와 비교 한계를 `docs/T16_ENGINE_MODEL_DECISION.md`에 기록한다. 명세 9.1의 구현 부록에는 선택 결과·버전과 결정 문서 링크를 반영한다. 사용자 답변 전에는 로컬 검토 자료와 선택 대기 상태를 제시하고 선택 부분을 비워 둔다.

## 6. 검증 및 Phase 1 제출

- 분할 경계·마지막 구간·시각 복원, coverage/RTF 집계, turbo 후보별 검증과 기존 후보 호환성을 합성 입력으로 테스트한다. 최소 3개 샘플 × 4개 조합의 실행 목록을 로컬 manifest와 대조한다. 실행 실패와 사용자 검토가 필요한 항목은 드러내고 로컬 검토 링크를 직접 확인한다.
- `docs/DEVELOPMENT.md`에 검증한 실행·재현 명령을 기록한다. 최종 소스에서 unsigned macOS arm64 전체 build/test와 SwiftPM benchmark CLI build를 수행한다. 기존 단위·통합 테스트와 명령의 호환성을 확인하고 실제 통과·실패·건너뜀 수 및 결과 경로를 보고한다. CI는 실제 강의·모델 다운로드 없이 동작해야 한다.
- 사용자 선택을 기록한 뒤 staged diff 및 데이터 정책을 점검하고, T16 task 브랜치에만 commit/push한다. 최종 task SHA의 CI가 성공하면 **T16 — review ready**로 제출한다. 결과 보고에는 브랜치·SHA·CI 링크, 실제 비교한 후보/샘플 수와 길이, 완주/실패 건수, 다섯 평가 항목, 사용자 선택과 로컬 검토 파일, 결정 문서, 테스트 결과를 포함한다. `PROJECT_STATUS.md`, 계획 체크리스트, dev 통합과 브랜치 삭제는 독립 검토 후 별도 통합 지시에서 처리한다. T17이나 G2 승격은 이 세션에서 시작하지 않는다.
